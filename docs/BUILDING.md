# Building and packaging Otis

How the binary is built, what each platform's artifacts are, and the platform
facts that shaped those choices. Cutting a release is `docs/RELEASING.md`;
this document is what a release is made of.

Otis is **one binary**: with no arguments it opens the window, with arguments
it runs a command (`docs/FORMAT.md` §8). Every artifact below contains that
same binary, with one exception on Windows that has its own section.

## 1. Prerequisites

| | Needed for |
| --- | --- |
| Go 1.25+ | everything |
| Node 22+ and npm | the frontend bundle, which is embedded in the binary |
| `wails3` (v3.0.0-beta.16) | the build and packaging tasks |
| Docker | cross-compiling to Linux, or to macOS/Windows from a non-native host |
| `makensis` (NSIS) | the Windows installer; native on Windows, `brew install makensis` elsewhere |

The wails3 beta moves. The task names in this document were confirmed against
**v3.0.0-beta.16**; check `wails3 task --list` after upgrading.

```bash
wails3 task --list          # every task, with its summary
wails3 build                # the host platform's binary -> bin/otis
wails3 package              # the host platform's installers
```

## 2. One binary, two builds

`main.go` is the entry point and decides nothing except which half runs. The
desktop app lives in `gui.go` behind `//go:build !otis_cli`; `gui_disabled.go`
is the other side of that tag.

The tag exists so the command line can be installed with nothing but a Go
toolchain:

```bash
go install -tags otis_cli github.com/otis-http/otis@latest
```

Without it the build needs two things a CLI user should not have to supply.
The frontend bundle, which is generated and so absent from a module fetched
from the proxy — and an embed pattern matching no files is a *compile* error.
And, on macOS and Linux, cgo plus a platform toolkit: Cocoa, or GTK4 and
WebKitGTK 6.0 development headers, which a Linux CI runner does not have.

With the tag, `go build` needs neither: the CLI compiles for darwin, linux and
windows on both architectures with `CGO_ENABLED=0`, and CI asserts exactly
that on every push. That check is doing double duty — it is also the
layering constraint from CLAUDE.md, that nothing outside `internal/services`
and `main.go` may depend on Wails, and the tag is what makes it verifiable
rather than merely intended.

A tag-*less* `go install` still works, and deliberately: `frontend/dist/.gitkeep`
is tracked so the embed pattern always matches something. The binary that
results is a working `otis` command whose window declines to open and says
why (`assetsPresent` in `gui.go`), which is a far better failure than either
a compile error about an embed pattern or a window that renders nothing.

## 3. The build identity

`otis --version` and `otis version` print the same block:

```
otis v0.2.0
commit    1a2b3c4
built     2026-09-03T10:04:00Z
go        go1.25.5
platform  darwin/arm64
```

All five, because Otis ships **no auto-updater** — the update path is
`brew upgrade` or a fresh download — so "what are you running" has to be
answerable by hand and complete enough to paste into a bug report. Between two
tags there are a hundred builds that all call themselves the same thing, which
is why the commit is there.

The three stamped values live in `internal/buildinfo` and are set by the
linker. `Taskfile.yml` derives them:

| Variable | From |
| --- | --- |
| `VERSION` | `git describe --tags --always --dirty` |
| `COMMIT` | `git rev-parse --short HEAD` |
| `BUILD_DATE` | `date -u +%Y-%m-%dT%H:%M:%SZ` |

Any of them can be overridden: `wails3 build VERSION=1.2.3`. Pin `BUILD_DATE`
to make two builds of one commit byte-identical, which is what lets somebody
else reproduce a published checksum.

An unstamped binary — `go build`, or `go install` — reports `dev` with
`commit unknown`. That is the honest answer and the test asserts it.

**The window shows it too**, because without an updater the question gets
asked from inside the app as often as from a shell: the empty state's footer
carries `version · commit`, and ⌘P › `>` › **Copy version** is reachable with
a collection open. `DESIGN-NOTES` §9.18 has the reasoning. On macOS the About
panel shows the version as well, from `CFBundleShortVersionString`.

`internal/buildinfo` is deliberately not in `internal/services`: `cmd/otis`
must not import that package, because it pulls in Wails and the CLI has to
keep building with `CGO_ENABLED=0`.

## 4. What the version is stamped into

Three files carry a version and none of them is `internal/buildinfo`:

- **`build/config.yml`** `info.version` — the source for `Info.plist` and
  `info.json`, regenerated by `wails3 task common:update:build-assets`. Bumped
  by hand as part of cutting a release.
- **`build/darwin/Info.plist`** — `CFBundleShortVersionString` is overwritten
  *in the bundle* with the real `VERSION` by `darwin:stamp:plist`, so the
  About panel cannot be a tag behind `otis --version`. `CFBundleVersion` is
  left alone: it must be a monotonic dotted number and a `git describe` like
  `v0.2.0-3-gabc1234` is not one.
- **`build/linux/nfpm/nfpm.yaml`** — `version: "${OTIS_VERSION}"`, expanded
  from the environment by the packaging tasks using `PKG_VERSION`: the tag
  with no leading `v` and every `-` turned into `.`, because rpm forbids `-`
  in a Version.

> `wails3 task common:update:build-assets` **patches** the generated files
> rather than rewriting them, so a key it once wrote survives a config change
> that should have removed it. If a stale key needs to go, delete the file and
> re-run. That is how `CFBundleIconName` was removed.

## 5. Icons

`build/appicon.svg` is the source of truth and `build/appicon.png` is its
1024px render. **Both are committed**, because nothing in the build chain
rasterises SVG and CI must not need a rasteriser. After editing the SVG:

```bash
magick -background none build/appicon.svg -resize 1024x1024 \
  -depth 8 -define png:color-type=6 build/appicon.png
```

`common:generate:icons` derives everything else from the PNG — `icons.icns`,
`icon.ico`, and the `httpFileIcon` pair for the `.http` document type — so
those are generated, git-ignored, and never edited by hand.

Otis ships **no macOS 26 layered icon** (`build/appicon.icon` +
`Assets.car`). That format's foreground layer is a monochrome glyph over a
background the OS composites itself, and Otis' icon is a finished two-colour
mark that already carries its own rounded rectangle, so it does not decompose
into those layers without being redrawn as one. A *stale* bundle is worse than
none: `Assets.car` wins on macOS 26 while `icons.icns` is what every older
release draws, so the app would have had two different icons depending on the
OS. macOS renders an `.icns` app icon as authored on every version it
supports. To add one later, split `appicon.svg` into a background and the
ring-and-triangles glyph, build the bundle in Icon Composer, and restore the
`-iconcomposerinput`/`-macassetdir` flags in `build/Taskfile.yml`.

The `.http` **document** icon is currently the app icon. A document icon
proper is the mark on a page rather than a second copy of the app icon sitting
in Finder; that artwork does not exist yet (`DESIGN-NOTES` §9.18).

## 6. The `.http` file association

Double-clicking a `.http` file opens the collection around it and shows that
request. Four things make that work, and they are in four different places:

1. **`build/config.yml`** `fileAssociations` — one entry, `ext: http`,
   `role: Editor` (Otis writes the file back), `mimeType: text/x-http`. It
   generates `CFBundleDocumentTypes` in `Info.plist` and the
   `wails.associateFiles` macro in the NSIS installer.
2. **`main.go`** `FileAssociations` — on Windows and Linux this is what makes
   Wails recognise `argv[1]` as a file to open. macOS uses the `Info.plist`
   declaration and the NSApplication delegate instead.
3. **`cli.WindowPath`** — the argv rule. A file association arrives looking
   exactly like a command line, so something has to decide which it is: one
   argument, not a flag, not a command name, and it exists on disk. Every
   clause is load-bearing and every one has a test.
4. **`CollectionService.OpenPath`** — the single entry point for a path from
   outside the window. It finds the collection root with
   `collection.FindRoot`, the same walk `otis run` uses, so a request resolves
   against the same root from the desktop as from the terminal.

The window is told which node to show by **pulling**, not by being pushed:
`TakePendingOpen`. Wails raises its runtime-ready event before the React tree
has mounted, so a target emitted then is simply lost — which is exactly what
happened the first time this was tested: the collection opened and the window
sat on the empty centre pane. `events.OpenNode` remains as a nudge for a
window that is already open.

On **Linux** the association needs two more files, both committed and neither
generated:

- `build/linux/otis.desktop`, carrying `MimeType=text/x-http;`.
  `wails3 generate .desktop` writes a MimeType line only for custom URL
  *protocols*, so regenerating it silently drops the one line that makes the
  association work. `linux:generate:dotdesktop` asserts the line is present
  rather than producing the file.
- `build/linux/otis-http.xml`, the shared-mime-info package that teaches the
  system `*.http` is `text/x-http`. A subclass of `text/plain`, deliberately:
  a `.http` file *is* text, so every editor still offers to open one. Otis
  does not claim the type — the JetBrains HTTP Client and the VS Code REST
  Client read the same files, and that they can is the point of the format.

The deb and rpm install both and run `update-desktop-database`,
`update-mime-database` and `gtk-update-icon-cache` in `postinstall`. **The
AppImage cannot register a file association** — nothing about a single
executable file is installed system-wide — so `.http` association on Linux
needs the deb or the rpm.

## 7. Single instance

A second launch hands its arguments to the running instance and exits, rather
than starting a second Otis. That is what makes the file association behave:
without it, double-clicking a second `.http` file would open a second window
fighting the first over the same collection, the same watcher and the same
keychain prompts.

`SingleInstance.UniqueID` is `appIdentifier` in `main.go`,
`io.github.otis-http.otis` — the same string as the macOS bundle identifier,
because both answer "which app is this" and a second answer would be a second
app as far as the OS is concerned. On Linux, Wails turns it into the D-Bus
name `org.io.github.otis-http.otis.SingleInstance`.

A relative path in a forwarded command line is resolved against the
**sending** process's working directory (`cli.WindowPathIn`), not the running
instance's — which for an app launched from Finder is `/`. Getting that wrong
fails silently: the path does not exist, so the rule decides it was never a
path, and the file is dropped. That bug existed and has a test.

**Known limit, macOS.** A forwarded launch raises the window within Otis but
does not raise Otis above another application: that needs
`-[NSApplication activateIgnoringOtherApps:]` and Wails v3 beta.16 exposes no
cross-application activate. It costs nothing in the cases a user meets —
double-clicking the app, a `.http` file, or the Dock icon all go through
LaunchServices, which activates Otis itself and never reaches that code. What
is left is `otis file.http` typed in a terminal while the app is open: the
file opens in the window, and the window has to be switched to by hand.

## 8. macOS

```bash
wails3 task release:darwin      # universal .app + DMG + tar.gz into dist/
```

- **Universal**, arm64 + amd64, joined with `lipo`. `release:darwin` uses
  `darwin:package:dmg:universal` rather than `package:dmg` on purpose: the
  latter builds for the host only, which on an Apple Silicon machine produces
  an arm64-only DMG that an Intel Mac cannot run at all, and nothing about the
  artifact says so.
- The bundle is **`Otis.app`** while the executable inside is `otis`. An
  `otis.app` in /Applications sits among `Xcode.app` and `Safari.app` looking
  like a mistake; `Info.plist` already carries `CFBundleName=Otis` with
  `CFBundleExecutable=otis`.
- **Ad-hoc signed** (`codesign -s -`) so it runs on the machine that built it.
  Not Developer ID signed and not notarized: users will meet Gatekeeper. See
  `docs/RELEASING.md`.
- Deployment target **macOS 12**.
- The CLI works from inside the bundle:
  `Otis.app/Contents/MacOS/otis ls`.

## 9. Windows

```bash
wails3 task release:windows     # NSIS installer + CLI zip into dist/
```

- `CGO_ENABLED=0` holds, and is asserted by the task's environment. The
  Windows build therefore needs no C toolchain and cross-compiles from
  anywhere Go runs.
- The installer is **NSIS**, machine scope by default, and includes the
  **WebView2 bootstrapper** (`wails3 generate webview2bootstrapper`) so a
  machine without the runtime gets it during install.
- It registers the `.http` association and copies `httpFileIcon.ico` into
  `$INSTDIR`. A missing icon file **fails the installer build**, which is why
  `generate:icons` produces it unconditionally.
- **amd64 by default**, not the host's architecture: built on an arm64 Mac an
  inherited `ARCH` would quietly produce an arm64 installer almost no Windows
  user can run. `ARCH=arm64` overrides.
- Unsigned, so users will meet SmartScreen. See `docs/RELEASING.md`.

### The Windows CLI

This is the one place "the CLI is the same binary" needs an asterisk.

The packaged `otis.exe` is linked `-H windowsgui`, without which a console
window flashes up behind every launch, including a `.http` file opened from
Explorer. A GUI-subsystem process on Windows has two consequences:

1. It starts with **no standard handles**, so its output goes nowhere.
   `cmd/otis/console_windows.go` fixes this: `AttachConsole(ATTACH_PARENT_PROCESS)`
   borrows the parent shell's console, and the handles the process was *given*
   win when it has them, so `otis ls > out.txt` and `otis ls | more` keep
   working rather than printing to the screen and leaving the file empty.
2. It is **never waited for**. cmd.exe returns to the prompt immediately and
   never sees the exit code. This cannot be fixed from inside the child, and
   it means `otis run` cannot gate a Windows CI step.

So the release also ships a **console-subsystem build of the same source**,
one differing linker flag, as `otis_<version>_windows_<arch>.zip`. That is the
binary to put on PATH and the one to use in CI; `go install` produces a
console binary too, for the same reason. The installer's binary is the GUI
one. `windows:build:cli` is the task.

## 10. Linux and WebKitGTK

```bash
wails3 task release:linux       # AppImage + deb + rpm + tar.gz into dist/
```

Linux needs CGO, so building it from a non-Linux host goes through Docker:

```bash
wails3 task setup:docker        # builds the wails-cross image (~800MB)
```

**Otis links against GTK4 + WebKitGTK 6.0**, which is what Wails v3 targets.
That sets the distro floor, and it is a high one:

| | Ships `libwebkitgtk-6.0-4` |
| --- | --- |
| Ubuntu | 24.04 and later |
| Debian | 13 (trixie) and later |
| Fedora | 39 and later (`webkitgtk6.0`) |
| RHEL / Alma / Rocky | 10 and later |
| Arch | current (`webkitgtk-6.0`) |

Two things set that floor, not one. The **WebKitGTK version** Otis links
against, above — and the **glibc of the machine that built it**, because a Go
binary using cgo links glibc dynamically and will not start on a system with
an older one. Nothing in the artifact announces either. So the release builds
Linux on a pinned `ubuntu-24.04` runner rather than `ubuntu-latest`: a runner
that rolls forward would raise the minimum glibc a user needs, silently, in a
release nobody marked as different. 24.04 is also where
`libwebkitgtk-6.0-dev` first appears, so the two floors coincide by
construction rather than by luck.

**Ubuntu 22.04 and Debian 12 cannot install the deb**, and the AppImage will
not start on them either — an AppImage bundles the app, not the system WebKit.
Wails can still be built against the older WebKit2GTK 4.1 with `-tags gtk3`,
supported through v3.0.x and **removed in v3.1**. Otis does not ship such a
build: it would be a second artifact per architecture, against a stack that is
being removed, for distros whose own successors are already out. The
dependency set for one is written down in a comment at the bottom of
`build/linux/nfpm/nfpm.yaml` so the option is recorded rather than
rediscovered. A user on an older distro should use the CLI, which needs none
of this — `go install`, or the tar.gz.

Note also:

- The **AppImage cannot register the `.http` association** (§6). Use the deb
  or the rpm for that.
- **Arch packaging exists but is not released.** `linux:create:aur` works, but
  a PKGBUILD we generate would go stale the moment somebody maintains one
  properly, and there is nowhere to publish it that Arch users look. The
  AppImage covers Arch.
- **amd64 by default**, as on Windows.

## 11. Artifacts and checksums

```bash
wails3 task release:checksums   # SHA256SUMS over everything in dist/
```

`dist/` is the release directory. Names are
`otis_<version>_<os>_<arch>.<ext>`, version without its leading `v`:

| Artifact | What it is |
| --- | --- |
| `otis_<v>_darwin_universal.dmg` | the app, for people |
| `otis_<v>_darwin_universal.tar.gz` | the bare binary — Homebrew, CI |
| `otis_<v>_windows_amd64_setup.exe` | NSIS installer, GUI binary |
| `otis_<v>_windows_amd64.zip` | the console CLI binary, for PATH and CI |
| `otis_<v>_linux_amd64.AppImage` | the app, no install |
| `otis_<v>_linux_amd64.deb` / `.rpm` | the app, with the file association |
| `otis_<v>_linux_amd64.tar.gz` | the bare binary |
| `SHA256SUMS` | **the only integrity signal Otis ships** |

Nothing is signed, so the checksums matter more than they otherwise would:
they are generated last, over whatever is in `dist/`, sorted and with no
directory component so `shasum -c SHA256SUMS` works in a download folder.

The archive is not redundant with the installer. It is what `brew install`
consumes, what a CI job unpacks, and the only artifact somebody can use
without running an installer.

**Build, sign and package are separate steps**, and `sign:darwin`,
`sign:windows` and `sign:linux` are currently no-ops that say so. They exist
so that signing later is an edit to one task rather than a rework of the
release tasks. `docs/RELEASING.md` says exactly what would go in each.

## 12. Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request:
`go vet ./...`, `go test -race ./...` and the frontend typecheck once on
Linux, then build **and package** on all three platforms, uploading every
artifact so a pull request can be installed and tried rather than only
compiled. A green `go test` has never once caught a broken NSIS installer.

Two checks there are worth knowing about because they guard invariants rather
than behaviour: the generated TypeScript event mirror must match the Go
constants (`go generate ./internal/events` leaves no diff), and the `otis_cli`
build must succeed for every platform with `CGO_ENABLED=0`, which is the
layering constraint from CLAUDE.md made verifiable.

`.github/workflows/release.yml` runs on a `v*` tag and is documented in
`docs/RELEASING.md`. Note that it uses `go vet ./...` and never
`go build ./...`: `build/ios` is a Wails scaffold whose main package has no
main function, so `go build ./...` fails on it and always has.

## 13. Verification

`go test -race ./...` covers the argv rule (`cli.WindowPath`), the build
identity (`internal/buildinfo`), root discovery (`collection.FindRoot`) and
the open path (`CollectionService.OpenPath`). What tests cannot cover is
whether the operating system delivers the events at all, so a release should
check by hand, per platform:

1. `otis --version` prints five stamped lines from the packaged binary.
2. `otis ls` and `otis run` work from the packaged artifact.
3. Double-click a `.http` file with Otis **closed**: it opens at that request.
4. Double-click a *different* `.http` file with Otis **open**: a second tab
   opens in the same process.
5. Run the binary directly while Otis is open: it exits 0, no second process
   appears, and the window navigates to the file it was given.
6. The window shows a version (empty state footer, or ⌘P › `>` › Copy
   version).

Steps 3–5 are observable without a screenshot: the window's open tabs and
active tab are persisted, so
`~/Library/Application Support/otis/settings.json` (or the platform
equivalent) records what actually happened.
